# UB host–device control and data-transfer reference

This is the UB counterpart of the supplied PCIe table, based on the Ascend950/A5 paths examined in the local CANN runtime and driver sources. UB uses several mechanisms here: address-based READ/WRITE, message-based SEND/RECV, and CPU access to explicitly mapped resources. A PCIe BAR entry therefore does not have one universal Jetty replacement.

Source snapshot: **2026-09-22**, driver commit `866e409`, runtime commit `216912472`. Feature flags, connection type, and queue mode select the applicable implementation. This document describes source behavior; it is not a measured hardware memory map. The external URMA/UDMA/UBCORE/UMMU implementations and the complete device firmware are outside this checkout.

The five columns retain the original table's purpose. **API** now names the software entry or helper instead of a BAR number. **Interface** names the observed access mechanism. Directions describe **payload movement**, not which side initiates the operation. Original PCIe capacities and window sizes—including 58 MB, 128 MB, and 128 GB—are not established UB sizes and are not carried over.

Here, “Jetty operations” includes operations submitted through JFS/JFR resources: JFS is the send work queue, JFR holds posted receive buffers, JFC records transport completions, and JFCE provides completion-event notification. “Partial” means that a related implementation is visible but the exact replacement of the original hardware region is not established.

## UB equivalent table — quick reference

This compact table follows the supplied PCIe table's **13-row order and five-column format**. Parentheses identify the corresponding original row. Sizes and BAR numbers are omitted because the traced UB mechanisms do not establish equivalent apertures. The source evidence and mapping limits are expanded in the next section.

## How to interpret the table

**The bus does not select a different public SQ API in every case.** For the normal queue mode examined here, `halSqTaskSend` explicitly dispatches PCIe/HCCS/RC connections to `trs_sq_task_send` and UB connections to `trs_sq_task_send_urma`. The UB implementation uploads SQEs and the tail using WRITEs. The runtime also has software-SQ/graph paths that cache work rather than immediately entering this branch, so “every stream task immediately calls the UB sender” is too broad. [HAL dispatch][sq-dispatch], [runtime submission branches][runtime-submit].

**SEND/RECV and READ/WRITE express different contracts.** A message delivers content to a peer receive/service endpoint; that content may be a command, metadata, or actual application bytes. READ/WRITE transfers bytes using address/segment permissions. Some service operations use SEND/RECV because the peer must interpret and execute a request. Selected registers instead have explicitly imported segments and supported READ/WRITE helpers. Possessing a numeric address alone is not sufficient permission or evidence that an arbitrary register supports Jetty access. [Kernel SEND][kernel-send], [kernel READ/WRITE][kernel-rw], [registered register targets][reg-op].

**A transport completion is not a device-task completion.** Finishing an SQ upload only accounts for the transport work; the device still needs to consume and execute the SQEs. Task results arrive through the task-CQ report path. Likewise, a service-message reply and an HDC send completion have different meanings. Interrupt/event delivery is used to notify software of relevant completions; it is not required for hardware to move every byte. The visible CQ path polls completion records after a callback and rearms event delivery. [SQ upload][sq-write], [task-CQ receive][cq-dispatch].

**UB also permits mapped CPU access.** In this source, the boot resource mapper is concrete evidence; the general architecture likewise supports both load/store and DMA communication. This does not make all UB memory or registers CPU-mappable. The `CFG_FEATURE_SLAVE_MODE` mapping path and the UBIOS loading path must be interpreted with their respective build guards, not combined into one mandatory boot sequence. [Resource mapping][ub-resource-map], [UBIOS callbacks][boot-ubios], [openEuler UnifiedBus architecture](https://docs.openeuler.org/zh/docs/24.03_LTS_SP3/server/releasenotes/releasenotes/key_features.html).

The unresolved physical-map items are the exact MSI-X/provider interrupt implementation, the selected UB topic-register/report mapping, the original SoC doorbell aperture, and the specific pre-HBM bootlog route. Resolving those requires the corresponding provider, firmware, platform configuration, or hardware documentation; the functional paths above do not determine their addresses or capacities.
